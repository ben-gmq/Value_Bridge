## 1. 業務機能体系（BFC：第1〜5階層）

> **プロセス＝各枝の最下層ノード（D-23）。** 第5階層固定ではなく、枝が第4階層で終わればその第4階層がプロセスです（第3〜5階層）。
> 業務要件（BR）はプロセス1件につき1件。プロセスには子ノードを追加できません（分割する場合は先にBRを廃止）。

| 機能ID | 機能名 | 概要 |
|---|---|---|
| `create_bfc_node` | 業務機能ノード登録 | 第1〜5階層の業務機能を階層登録。プロセス（最下層）の作成時に業務要件を同一トランザクションで1件自動生成 |
| `mark_process` | プロセス指定・解除 | 子のない第3〜5階層ノードをプロセスに指定（BRを自動生成）。BRが有効な間は解除不可 |
| `generate_bfc_code` | 階層コード自動採番 | 親階層をたどり `01.02.03.04.05` 形式のコードを保存時に生成 |
| `reorder_bfc_node` | 並び順変更 | 兄弟ノードの並び替えと配下全ノードのコード再計算を1トランザクションで実行 |
| `link_bfc_data_entity` | 入出力データ紐付け | プロセスに入力・出力データエンティティを各0..N件紐付け。**業務フロー・DFD・業務要件が同じ記録を参照**（D-24）。BRのCRUDが依存している間は削除不可 |
| `create_external_entity` | 外部エンティティ登録 | 顧客・銀行・規制当局・取引先など組織外の当事者。`EXT-0001` 形式 |
| `link_bfc_external_flow` | 外部データ授受紐付け | プロセスと外部エンティティ間のデータの流れ（方向・データエンティティ）|
| `link_bfc_role` | 実施組織・役割紐付け | プロセスに実施役割をRACI区分で紐付け。Accountableは1件のみ |
| `link_bfc_application` | 現行システム紐付け | 当該業務を現在支えているシステムを紐付け（As-Is） |

## 2. 業務フロー図・DFD（BFC・データエンティティ・業務要件から生成）

| 機能ID | 機能名 | 概要 |
|---|---|---|
| `link_process_flow` | 業務フロー接続登録 | プロセス間の流れを登録。順次／条件分岐／並行／他領域への引継の4種。分岐には条件ラベルが必須 |
| `generate_process_flow` | 業務フロー図生成 | 親ノードを指定し、配下のプロセス（階層を問わず最下層）を処理ボックス、実施役割をスイムレーン、入出力データをデータストアとしたフロー図データを生成 |
| `export_process_flow` | 業務フロー図エクスポート | 同じフロー図を Mermaid 形式のテキストで出力。資料への貼り付け用 |
| `flow_completeness_report` | フロー整備状況レポート | 接続のない孤立ステップ、開始・終了のないプロセス、ラベルのない分岐、**出力データのないステップ**を検出 |
| `generate_dfd` | DFD生成 | 同じデータから順序を除いた論理DFD：プロセス・データストア・外部エンティティ・データの流れ（D-31）|
| `export_dfd` | DFDエクスポート | Mermaid形式で出力 |
| `download_flow_schema` | JSONファイル仕様の提供 | `vb-process-flow/1.0` のJSONスキーマ、記入例、**AI変換用プロンプト集**を提供（D-25）|
| `validate_process_flow_json` | 業務フローJSON取込検証 | PowerPoint・BPMN・Visio等からAIで変換したJSONを検証。エラー（取込不可）と警告（取込可）を元図の位置（例：4枚目・図形12）付きで表示。**業務テーブルには書き込まない** |
| `commit_process_flow_json` | 業務フローJSON取込確定 | 新規プロセス・BR・データエンティティ・接続を1トランザクションで作成。「追加」モードは既存を削除せず、「置換」モードは削除件数の確認が必須 |
| `export_process_flow_json` | 業務フローJSON出力 | 同じ形式で出力し、編集後に再取込可能 |

> **AIによる変換はVBの外で行います。** VBはJSONの仕様とプロンプト集を提供し、変換後のファイルを受け付けるだけで、顧客情報をAIサービスへ送信しません。

> **As-Is / To-Be は同一定義の二通りの描画です。** 処理・レーン・データストアは共通で、各ステップに紐づく
> システムのみが切り替わります。**この2枚の差分が変革そのもの**であり、従来手作業で描いていた図に相当します。
>
> 業務フローは往復（差戻し）ループを許容します。ソリューション依存関係とは異なり、
> 「差戻し→修正→再申請」は正常な業務動作であるためです。

## 提供順序（ウェーブ）

設計仕様書 §12.1 に対応します。**いずれも必須要件であり、順序のみが判断事項です。**

| ウェーブ | 対象 | 理由 |
|---|---|---|
| **1** | 第1〜10章、第15章 | スコープ管理の中核。規模・工数（第10章）は後付け不可 — 工数を持たずに確定したベースラインは永久に金額換算できないため |
| **2** | 第11章（効果）、第13章（変更管理） | 「追加するなら何を削るか」を実行可能にする組合せ |
| **3** | 第12章（リスク）、第14章（フェーズ） | 単独で成立し、他機能を阻害しない |

## 補足：本アプリケーションにおける「コントロール」の定義

**コントロールとは変更を起こさせないことではありません。** プロジェクトに変更は必ず発生します。
コントロールとは、変更を**意図的に吸収する能力**——早期に検知し、金額換算し、判断し、再ベースライン化する——を指します。
変更が一切記録されていないプロジェクトは、統制されているのではなく、検証されていないだけです。

第15章のコントロールルールは、各分析に**閾値・責任役割・対応策**を与えます。
閾値のない分析は、誰も行動しないレポートにすぎません。
