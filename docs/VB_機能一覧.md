# Value Bridge 機能一覧

**対象読者：** 日本語で本アプリケーションの全体像を把握する必要があるプロジェクト関係者
**典拠：** `docs/VB_design.md`（設計仕様書、2026-10-13 統合版・S10d-1まで）§4 業務要件グリッド、§12.1 提供順序
**版数：** 2026-10-14 改訂（D-32〜D-64：コンポーネント、アクセス制御、DFD一本化、BR↔FR直接紐付け、ベースライン承認等を反映） · **全 122 機能**

> 機能IDは設計仕様書上の識別子であるため英語表記のままとしています。
> 実装単位・API単位もこのIDに対応します。コード値（`TO_BE`、`SOLUTION` 等）も英語のままです。

> **コンポーネント（D-37）。** プロジェクトごとに使用するコンポーネント（機能のまとまり）を選択します（第9章 `set_components`）。
> オフのコンポーネントへの書込みは **409 `COMPONENT_OFF`** で拒否され、画面上も非表示になります（参照は可能）。
> 各章の「コンポーネント」はその機能が属するものです。常時オン：To-Be業務機能体系、業務要件とそのCRUD、プロセス入出力、RACI、データエンティティと項目、組織図、外部エンティティ、関係者。

## 1. 業務機能体系（BFC：第1〜5階層）

> **プロセス＝各枝の最下層ノード（D-23）。** 第5階層固定ではなく、枝が第4階層で終わればその第4階層がプロセスです（第3〜5階層）。
> プロセスには子ノードを追加できません。
> **体系は2種類（D-47）。** 必須の **To-Be（あるべき姿）** と、任意の **As-Is（現状）**（コンポーネント `AS_IS`）。
> 業務要件（BR）は **To-Be のプロセス1件につき1件** で、As-Is のプロセスにはBRを持ちません。

| 機能ID | 機能名 | 概要 |
|---|---|---|
| `create_bfc_node` | 業務機能ノード登録 | To-Be または As-Is の体系に第1〜5階層の業務機能を階層登録。名称は有効な兄弟ノード間で一意。**To-Be のプロセス作成時は業務要件を同一トランザクションで1件自動生成** |
| `mark_process` | プロセス指定・解除 | 子のない第3〜5階層ノードをプロセスに指定（To-Be ならBRを自動生成）。解除は、BR・入出力・役割・外部データ授受・現行システム・トリガー・実施主体・処理内容のいずれかが残っていれば **409 で全件を列挙して拒否**。VBが自動で廃止することはなく、利用者が個別に廃止してから解除 |
| `describe_process` | 処理内容記述 | プロセスのデータ処理内容をシステムに依存しない表現で記述。プロセス以外のノードには不可 |
| `generate_bfc_code` | 階層コード自動採番 | 親階層をたどり `01.02.03.04.05` 形式のコードを保存時に生成。体系ごとに一意 |
| `reorder_bfc_node` | 並び順変更 | 兄弟ノードの並び替えと配下全ノードのコード再計算を1トランザクションで実行 |
| `link_bfc_data_entity` | 入出力データ紐付け | プロセスに入力・出力データエンティティを各0..N件紐付け。**DFD・業務フローJSON・業務要件が同じ記録を参照**（D-24）。BRのCRUDまたは外部データ授受が依存している間は削除不可（依存元を列挙） |
| `create_external_entity` | 外部エンティティ登録 | 顧客・取引先・銀行・規制当局・パートナー等、組織外の当事者。`EXT-0001` 形式 |
| `link_bfc_external_flow` | 外部データ授受紐付け | プロセスと外部エンティティ間のデータの流れ（方向・データエンティティは任意）。データエンティティを指定した場合、対応するプロセス入出力を同一トランザクションで自動追加 |
| `link_bfc_role` | 実施役割紐付け（As-Is） | **As-Is プロセスのみ**（D-64）。役割をRACI区分で紐付け。Accountableは1件のみ、Responsibleは複数可。To-Be プロセスの役割は業務要件側で管理（第4章 `link_br_role`） |
| `link_bfc_application` | 現行システム紐付け | **As-Is プロセスのみ**。当該業務を現在支えているシステムを紐付け。To-Be のシステムは BR→ソリューション→システム から導出 |
| `retire_step_with_dependents` | プロセス一括廃止・復元 | **VBで唯一の連鎖処理。** プロセスと、それに従属する行（BRとそのCRUD・役割・ソリューション／機能要件紐付け、入出力・役割・外部データ授受・現行システム・トリガー紐付け）をプレビュー・確認のうえ一括で論理削除。復元も同じ単位で全件一括 |

## 2. DFD（データフロー図）・業務フローJSON

> **業務フロー図は廃止し、全プロセスをDFDで表現します（D-38）。** DFDは業務機能体系・入出力・外部データ授受・トリガー・実施主体から**生成**され、手で描くものではありません（D-31）。
> **処理順序はデータから導出し、保存しません。** プロセスAが出力したデータをプロセスBが入力すれば「A→B」。分岐は異なる出力（例：「承認済注文」／「却下注文」）が別プロセスに渡ること、差戻しループは後工程が前工程の入力を書き戻すことで表現されます。
> 従来の「業務フロー接続」（順次・分岐・並行・引継の矢印）は廃止され、履歴として参照のみ残ります。

| 機能ID | 機能名 | 概要 |
|---|---|---|
| `copy_bfc_set` | 体系の複製（As-Is⇔To-Be） | 一方の体系を**空の**もう一方へ丸ごと複製（D-47）。プレビュー確認後に実行。ノード・実施主体・入出力・外部データ授受・トリガーを複製し、役割は移動先の管理場所（BR側／プロセス側）へ移す。As-Is→To-Be ではプロセスごとに新規BR（下書き）を採番。BRのCRUD・ソリューション・機能要件は複製しない |
| `set_performer` | 実施主体設定 | プロセスごとに実施主体を1つ：部門・役職・ITシステム・AI（D-46）。未設定も可（「未割当」レーンに表示され警告、ベースライン確定は妨げない）。実施中のプロセスがある部門・役職・システムは廃止不可 |
| `maintain_process_trigger` | トリガー（起動契機）管理 | プロジェクト共通のトリガー一覧。種別は時刻（TIME、スケジュール注記付き）／イベント（EVENT）（D-49） |
| `link_process_trigger` | トリガー紐付け | 「このトリガーがこのプロセスを起動する」を登録。プロセスとともに廃止・復元 |
| `generate_dfd` | DFD生成 | 任意の非プロセスノードを指定し、配下のプロセスを**実施主体ごとのスイムレーン**に配置。データストア・外部エンティティ・トリガー（開始記号）・データの流れ、データから導出した順序と左→右の段組（ループ可）、範囲外プロセスとの境界、整備状況の不足、保存済みの配置を返す。プロセス枠には As-Is は現行システム、To-Be は BR→ソリューション→システム を表示 |
| `dfd_index` | DFD一覧 | DFD画面（D-54）。プロセスの直接の親ノードごとに1枚、コード・名称・プロセス数を一覧（階層表示なし、検索可）。選択すると描画。上位階層をまとめた図は業務機能体系から開く |
| `export_dfd` | DFDエクスポート | Mermaid形式のテキスト（レーンごとのサブグラフ、トリガーを開始ノード、順序は指定時のみ破線）。全ラベルをエスケープ |
| `process_completeness` | プロセス整備状況チェック | 各プロセスに**入力（入力データ・外部からの受信・トリガーのいずれか）と出力データ**が必要（D-38、D-49）。不足は編集画面で警告し、**ベースライン確定を阻止**（そのDFDコンポーネントがオンの体系のみ）。実施主体未設定、BR未生成（To-Beのみ）、入出力と不一致のCRUD・外部データ授受等も検出 |
| `download_flow_schema` | JSONファイル仕様の提供 | `vb-process-flow/2.0` のJSONスキーマ、記入例、**AI変換用プロンプト集**を提供（D-25）。**利用可能なAIはFTC契約のClaudeまたはMicrosoft Copilotのみと明記し、個人情報の除去手順から始まる**（D-36） |
| `export_process_flow_json` | 業務フローJSON出力 | 親ノード配下のプロセスを出力：BR番号（To-Beのみ、識別子）、階層コード（照合用）、版番号、名称、説明、実施主体、入力・出力、トリガー、外部データ授受。**矢印・レーンは含まない**。編集後に再取込すると更新として扱い、古い版は検出 |
| `validate_process_flow_json` | 業務フローJSON取込検証 | 基点ノードとモード（追加／置換）は画面で選択。BR番号で既存プロセスを特定し、階層コード・版番号で「出力後に移動・更新されていないか」を照合。**警告のみで取込可（D-55）**：入出力のないプロセス、未接続のプロセス、未登録のデータエンティティ（新規作成）・トリガー（追加）・実施主体（空欄）等。**エラーはデータを損なう場合のみ**：読めないファイル、旧形式（1.0）、基点・モードの不一致、古い版番号。**業務テーブルには書き込まない** |
| `commit_process_flow_json` | 業務フローJSON取込確定 | 1トランザクションで全件成功か全件却下。新規件数・廃止件数の確認入力が必須。新規プロセスにはBRを自動生成。「追加」モードは何も廃止せず、「置換」モードが廃止するのは入出力とトリガー紐付けのみ。取り込んだ不足はDFDの警告として残り、**不完全なDFDは取込はできるが確定はできない** |

> **AIによる変換はVBの外で行います。** VBはJSONの仕様とプロンプト集を提供し、変換後のファイルを受け付けるだけで、顧客情報をAIサービスへ送信しません。

> **As-Is / To-Be はそれぞれ独立した体系とDFDを持ちます（D-47）。** データエンティティ・外部エンティティ・トリガー・組織図・システムは両者で共有するため、
> 同じ `DE-` 番号で比較できます。**この2枚の差分が変革そのもの**であり、従来手作業で描いていた図に相当します。
> コンポーネント：To-Be は `TO_BE_DFD`、As-Is は `AS_IS`。

## 3. データエンティティ管理

| 機能ID | 機能名 | 概要 |
|---|---|---|
| `create_data_entity` | データエンティティ登録 | `DE-0001` 形式で保存時に自動採番。名称は有効なエンティティ間で一意 |
| `manage_data_fields` | データ項目管理 | 主キー・外部キー・主要属性を管理。複合主キー対応。**論理モデルのため全項目の定義は不要、データ型も任意**（D-26）。外部キーは同一プロジェクト内のエンティティのみ。プロジェクトの詳細度設定にかかわらず追加項目は常に登録可（D-39） |
| `validate_entity_model` | モデル整合性検証 | 主キー未設定、参照先に主キーがない外部キー、項目未定義のエンティティを検出。**詳細度 `FULL` の場合はキーのみで属性のないエンティティも検出**（D-39）。警告のみ |
| `generate_erd` | ERD生成 | エンティティと外部キーから論理ERDを自動生成。カラス足記法、外部キーの必須性から多重度を判定。業務領域（サブジェクトエリア）で絞込み（D-29） |
| `export_erd` | ERDエクスポート | PNG・SVG・Mermaid形式 |
| `save_diagram_layout` | 図の配置保存 | ERD・DFDでドラッグした位置をオブジェクト単位で保存（後勝ち）。未配置の要素は自動レイアウト。配置のリセットは監査記録付き（D-30） |

> テーブルを生成するものではなく、**論理データモデル・論理DFD**を扱います。

## 4. 業務要件（BR）

> **業務要件は業務機能体系の一部です（D-53）。** 業務要件の一覧画面はなく、プロセスのパネルから参照・編集します（BR画面は機能要件・ソリューション・差分からのリンク先として残ります）。

| 機能ID | 機能名 | 概要 |
|---|---|---|
| `create_br` | 業務要件登録 | **To-Be のプロセス**ごとに1件。ノード作成・プロセス指定・体系複製時に自動生成され、`BR-0001` 形式で採番。初期状態は下書き |
| `update_br` | 業務要件更新 | 排他制御付き。他者が先に更新している場合は競合エラーを返し上書きを防止。「ベースライン済」「旧版」の状態はベースライン確定でのみ設定 |
| `link_br_data_entity` | 使用データ紐付け | CRUD区分で紐付け。入力／出力区分はCRUDから自動導出。**プロセスの入出力に未登録なら同時に追加**し、業務要件とDFDが常に一致（D-24） |
| `read_br_attributes` | 使用データ項目の参照 | 業務要件に紐づくデータエンティティの項目（名称・型・キー・必須）を一覧表示。参照のみ（D-60a） |
| `link_br_role` | 責任組織紐付け（RACI） | **To-Be プロセスのRACIはここで管理**（D-64）。Accountableは1件のみ（区分コードではなく振る舞いで判定するため、RASCI等にも対応） |
| `link_br_solution` | ソリューション紐付け | 業務要件と解決策の多対多紐付け。組合せごとに充足メモを保持。却下済ソリューションも紐付け可能だが網羅性には算入しない。コンポーネント `SOLUTION` |
| `link_br_fr` | 機能要件の直接紐付け | **業務要件→機能要件の主たる紐付け（D-52）。** 多対多、組合せごとに充足メモ。ソリューションがオフのプロジェクトでも利用可能。紐付けのある機能要件は廃止不可（紐付け元を列挙） |
| `set_fr_solution_from_br` | 業務要件画面での実現ソリューション指定 | 業務要件の機能要件行で、**その業務要件に紐づくソリューション**のうちどれで実現するかを選択（またはなし）。それ以外は拒否し、ソリューション紐付けを裏で自動作成することはない |
| `create_fr_from_br` | 業務要件からの機能要件作成 | 機能要件を作成し、同じトランザクションで業務要件に紐付け |
| `br_coverage_report` | 要件網羅性レポート | 出力データのない要件、解決策のない要件、機能要件のない要件（情報）、**業務要件に紐づかない機能要件（警告）**、ソリューション未指定の機能要件（情報）、指定ソリューションが紐付け先の業務要件に対応しない機能要件（警告）、未参照エンティティを一覧 |

> 構造化された要件記述（D-59）、項目単位のCRUD（D-60b）、業務要件上のシステム間データ連携（D-61）は方向性のみ決定済みで、スライス11で仕様化されてから本一覧に加わります。

## 5. ソリューション・機能要件・システム

| 機能ID | 機能名 | 概要 |
|---|---|---|
| `create_solution` | ソリューション登録 | `SOL-0001` 形式。組織・ルール／人／プロセス／データ／技術の5分類で管理（分類は全社固定）。初期状態は提案中。コンポーネント `SOLUTION` |
| `create_function_requirement` | 機能要件登録 | `FR-0001` 形式。機能種別（画面／インターフェース／帳票／バッチ）で分類。**ソリューションは任意**（D-28、D-52）。業務要件未紐付け、技術以外のソリューション、却下済ソリューション、同名重複は警告のみ |
| `set_fr_solution` | 実現ソリューション指定 | 機能要件ごとにソリューションを1つ（任意）指定。**紐付け先業務要件のいずれかに対応するソリューション**に限る（業務要件未紐付けなら任意）。工数をどのソリューションに計上するかを決める。後の紐付け変更で不整合が生じても拒否・自動解除はせず、レポートで検出 |
| `maintain_fr_types` | 機能種別の設定 | 案件ごとに種別の名称変更・追加・廃止が可能。各種別の「振る舞い」で画面の入力欄とIF一覧への掲載が決まる（D-27）。**使用中の全社種別の振る舞いは変更不可**（新しい種別を追加する） |
| `describe_interface` | インターフェース詳細 | 送信元／送信先システム、方式（Push／Pull／双方向）、手段（API／ファイル／DB／メッセージ／手作業）、頻度、件数メモ、連携データ（各注記付き）。コンポーネント `FUNCTION_REQUIREMENT` と `APPLICATION` |
| `interface_list` | インターフェース一覧 | **機能要件から自動生成**。機能要件番号がIF番号。**送信元・送信先・手段・連携データ1件以上で「完成」**、未完成も非表示にせず明示。システム組合せで絞込み、Excel出力 |
| `link_fr_to_bfc_node` | 業務機能への直接紐付け | 業務要件経由で表現できない範囲のみ。**設計済・未実装** |
| `create_application` | システム登録 | 現行／将来／両方の区分でシステム一覧を管理。システムコードはベースライン確定まで変更可。コンポーネント `APPLICATION` |
| `link_application_solution` | 実現システム割当 | どのシステムがその解決策を実現するか（To-Be）。現行のみのシステムは不可 |
| `solution_matrix` | ソリューション分類マトリクス | 分類×業務領域。**技術偏重の変革になっていないかを検知** |
| `application_gap_report` | システム移行ギャップ | 現行システムはあるが移行先が未定の業務＝移行課題一覧 |
| `fr_traceability_matrix` | トレーサビリティ表 | プロセス→業務要件→機能要件（直接紐付け経由）を機能種別ごとに一覧。ソリューション列は機能要件の指定値、システム列はその実現システム。業務要件に紐づかない機能要件は末尾に別掲 |

## 7. 一括アップロード／ダウンロード

対象：課題・データエンティティ・データ項目・業務要件・機能要件（D-28）・**WBS**（D-33）。業務フローJSON（第2章）も同じ取込処理を使用します。対象ごとにコンポーネントを検証・確定時に確認します。

| 機能ID | 機能名 | 概要 |
|---|---|---|
| `download_template` | テンプレート出力 | コードマスタ値をプルダウンとして設定済みのExcel様式 |

## 17. WBS取込と進捗管理

コンポーネント `WBS`。タスク一覧の正本はMS Projectのままで、VBは取り込んで各行にフェーズとソリューションを紐付け、**進捗を記録します**（D-33、D-41）。タスク作成・依存関係・ガントチャート編集・クリティカルパスは対象外です。

WBSの取込は第7章の一括取込処理を使用します。テンプレートはMS Projectの **Unique ID（必須）**・WBSコード・名称・アウトラインレベル・開始・終了・実績開始・実績終了・進捗率で構成され、日付形式（`yyyy-mm-dd`）への変換手順を記載します。行は Unique ID で特定し、「置換」モードではファイルにない行を廃止します。再取込してもフェーズ・ソリューション紐付けとVB上の進捗は変わりません。

| 機能ID | 機能名 | 概要 |
|---|---|---|
| `link_wbs_item` | WBS行の紐付け | フェーズとソリューションの設定・解除のみ。それ以外の項目は「MS Projectで変更して再取込」として拒否 |
| `record_wbs_progress` | 進捗更新の記録 | 取込行ごとに日付付きの進捗（進捗率・実績開始／終了・状況〔順調／要注意／遅延〕・コメント）を追加。上書きせず履歴として保持 |
| `wbs_progress_report` | 進捗レポート | VB上の進捗を基準に計画対実績、遅延日数、フェーズ別・ソリューション別の進捗率、最新コメント。**取込した実績とVB上の進捗が食い違う行を明示**。ベースライン対象外 |

## 補足：本アプリケーションにおける「コントロール」の定義

**コントロールとは変更を起こさせないことではありません。** プロジェクトに変更は必ず発生します。
コントロールとは、変更を**意図的に吸収する能力**——早期に検知し、金額換算し、判断し、再ベースライン化する——を指します。
変更が一切記録されていないプロジェクトは、統制されているのではなく、検証されていないだけです。

第15章のコントロールルールは、各分析に**閾値・責任役割・対応策**を与えます。
閾値のない分析は、誰も行動しないレポートにすぎません。
